# ProriumプラットフォームからのIR管理ログイン

既存のプラットフォームのマスターアカウントで株主レポートを管理する。IRの財務DBと株主ログインはIR専用のSupabaseプロジェクトに保持する。

## 利用導線

- プラットフォームのPC左メニューとスマートフォンのメニュー: **株主レポート管理** → `/shareholder-ir`
- IRログイン画面: **Proriumプラットフォームから管理画面へ**
- 有効な川上拓人のマスターアカウントからIRの `/admin` へ遷移する。

## 認証の流れ

1. IRの本番OriginでHttpOnly/Secure/Host限定の状態Cookieを作る（5分）。PKCE S256のチャレンジとstateをプラットフォームへ送る。
2. プラットフォームは `auth.getUser()` と `get_my_profile` で本人・有効状態・管理者ロール・指定UUIDを確認する。
3. サーバからIRの `ir-platform-sso` Edge Functionへプラットフォームのセッションを送る。ブラウザには既存セッションを渡さない。
4. Edge Functionが共通Authの `/user` とプラットフォームのプロフィールRPCで再検証する。IRの明示的なアカウント対応表と既存管理者権限を確認する。
5. 一度限り・60秒・PKCEに結びついたコードを発行する。DBにはコードのSHA256だけを保存する。
6. IRのCallbackはCookieのstate・期限を確認して、サーバからコードを交換する。DBで原子的に消費し、現在のIR管理者権限を再確認する。
7. Supabase Authが発行したログイントークンをIRサーバだけで検証し、通常のIRユーザーセッションを作る。RLS・操作監査・レビュー／承認／公開の権限制御が適用される。

## 保護

- 対応表とコード表はprivate schema、RLS有効、service_role以外のテーブル／RPC利用不可。
- Edge Functionは `verify_jwt=false` とし、関数内で発行元Authへ照会する。IRと共通Authは異なる発行元のため、IRのゲートウェイによるJWT検証は使えない。
- Edge Functionの特権キーはSupabaseが本番へ注入する。アプリの環境変数・ソース・フロントエンドにコピーしない。
- メール一致やuser_metadataで管理者を自動付与しない。対応表と既存のIR管理者権限が両方必要。
- キー、JWT、コード、OTPをログに記録しない。戻り先は固定した本番IR Originのみ。
- 認証済みプロフィールが停止／ロール変更された場合は新規ログインを拒否する。IRの管理者権限を削除した場合は既存セッションもRLSでアクセスできなくなる。
- 発行回数は1アカウントにつき5分間10回まで。期限切れ・消費済みコードは再利用不可。

## 運用

`private.platform_admin_links` の対応を無効にすると新規のプラットフォーム経由ログインを停止できる。IRの既存管理者権限やメールログインは独立して維持される。

本番反映後、未ログイン時の遷移と匿名／不正コード拒否を確認する。本人のブラウザでのログイン済み動作は、メニューを押して最終確認する。
