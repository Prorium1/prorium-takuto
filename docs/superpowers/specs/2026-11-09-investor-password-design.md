# Investor password issuance

The user wants investors to log in with a password automatically assigned by the company, alongside their email address and the site link. Keep the existing per-investor authorization and make email/password the primary login form. Email-link and platform login remain available.

The existing login action already uses Supabase `signInWithPassword`; the missing piece is admin provisioning. The admin page will register an investor and issue a unique password, or issue/reissue one for an active registered investor. Show the URL, email and password only in the issuing admin's current client state, with a copyable invitation and a dismiss button. No passwords in URLs, user metadata, audit records, persistent browser storage, or application tables. Supabase Auth manages password hashing. Issuance does not send an email automatically; the admin copies and sends the prepared invitation using their preferred channel.

Implementation choice: use a Supabase Edge Function with its injected server credentials and the supported Auth Admin API, following the existing SSO pattern. This avoids adding privileged keys to Vercel or editing Auth password hashes via SQL. A private RLS-enabled issuance record and bounded reservation serialize concurrent requests, track the target account, and record completion without secrets. Database guards require a confirmed administrator, an active investor invitation, and a target that is neither an administrator nor associated with another company. Reissue requires an explicit acknowledgement and never changes administrator credentials. Existing users must be associated with the current investor invitation; unrelated Auth accounts are protected.

Development uses synthetic inputs only. Do not issue or reset real investor passwords during deployment, send invitations, change report content, or publish reports. Verify the SQL guard matrix, password generation and external-operation failures, plus the primary login and credential-sharing interface. Production rollout adds empty private bookkeeping and new guarded functions before the frontend; existing invitation and login APIs remain compatible.
